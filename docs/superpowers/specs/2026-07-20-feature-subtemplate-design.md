# Design: `modulith-feature` — a feature sub-template shipped in the `Modulith` package

**Date:** 2026-07-20
**Status:** Approved (design); mechanics verified with a throwaway scaffold on .NET SDK 10.0.300.

## Problem

Adding a feature to a solution generated by this template is repetitive, error-prone
manual work. A feature is **four projects** under `src/Features/<Name>/`, named
`<App>.Features.<Name>.<Layer>` for `Layer ∈ {Domain, Application, Infrastructure, Web}`,
wired into a specific dependency chain, and each project must also be registered in the
`.slnx`. Doing this by hand for every feature is exactly the kind of boilerplate worth
automating.

## Goal

Give the developer of a *generated* project a one-command way to scaffold a new feature:
its four projects, their correct internal references, and their registration in the
solution — with no extra install step.

## Non-goals (deliberately deferred)

- **Host DI wiring** (registering a feature's services into `Program.cs` /
  `Infrastructure`). The host module-registration convention is not built yet in the
  template, so this stays a documented manual step.
- **An `IntegrationEvents` project** for cross-module communication (the architecture
  tests already anticipate an `.IntegrationEvents` namespace, but it is out of scope here).
- **A rich sample slice** (`--with-sample`). Generated features are bare skeletons,
  consistent with the current template state.

## Mechanism & distribution

A **second `dotnet new` template** lives in this repo alongside the solution template, and
both are packed into the **single existing `Modulith` NuGet package**. A template package
can contain multiple templates (each is its own `.template.config/template.json` folder);
installing the package makes all of them available. Because a developer already installed
`Modulith` to get `dotnet new modulith`, they automatically have `dotnet new
modulith-feature` — **no `dotnet new install .` step**.

No packaging-csproj change is required: `working/ModularMonolith.Template.csproj` already
packs `content/**` (excluding `bin`/`obj`), so a new `content/feature/` root is packed
automatically as a second template.

The "one template behind a parameter" alternative (e.g. `dotnet new modulith --feature X`)
was rejected: a template has a single `sourceName` and one content set, and "scaffold a
whole solution" vs. "add one feature to an existing solution" are genuinely different
operations. Two templates in one package is the idiomatic fit.

## Repo layout (new)

```
working/content/
  modulith/          # existing solution template (sourceName: ModulithTemplate) — unchanged
  feature/           # NEW feature template (sourceName: FeatureName)
    .template.config/template.json
    src/Features/FeatureName/
      ModulithApp.Features.FeatureName.Domain/         { .csproj, Placeholder.cs }
      ModulithApp.Features.FeatureName.Application/     { .csproj, Placeholder.cs }
      ModulithApp.Features.FeatureName.Infrastructure/ { .csproj, Placeholder.cs }
      ModulithApp.Features.FeatureName.Web/            { .csproj, Placeholder.cs }
```

Two independent placeholder tokens drive substitution:

- **`FeatureName`** — the feature name, handled by `sourceName` (replaced by `-n`).
- **`ModulithApp`** — the app prefix, handled by a required parameter symbol (`replaces` +
  `fileRename`).

Both tokens live only in `content/feature/`, completely separate from the solution
template's `ModulithTemplate` token, so the two templates never interfere. Baking the
`src/Features/FeatureName/` path into the template content — combined with
`preferNameDirectory: false` — means running from the generated solution's root drops the
projects into the correct location with no `-o` needed.

## `template.json`

Key settings:

- `shortName: "modulith-feature"`, `sourceName: "FeatureName"`,
  `identity: "ModularMonolith.Template.Feature"`, `preferNameDirectory: false`,
  `tags.type: "item"`.
- Required parameter symbol **`appName`**: `datatype: string`, `isRequired: true`,
  `replaces: "ModulithApp"`, `fileRename: "ModulithApp"`.
- `primaryOutputs`: the four `.csproj` paths.
- One post-action, **`D396686C-DE0E-4DE6-906D-291CD29FC5DE`** ("Add projects to solution"),
  `continueOnError: true`, `args.primaryOutputIndexes: "0;1;2;3"`.

## Generated project contents (bare skeleton)

Mirrors today's Orders feature **minus its intentional arch-test violation** — the
generated `Domain` references nothing:

| Project | References |
| --- | --- |
| `<App>.Features.<Name>.Domain` | (none) |
| `<App>.Features.<Name>.Application` | Domain |
| `<App>.Features.<Name>.Infrastructure` | Domain |
| `<App>.Features.<Name>.Web` | Application, `<App>.Web.Common` (via `../../../`) |

Each project gets one `Placeholder.cs` carrying the
`#pragma warning disable S2094` / `restore` empty-class suppression (same pattern as the
current `Class1.cs`), so a scaffolded feature builds **warning-clean under `-warnaserror`**
and passes both architecture tests immediately.

## Invocation UX

From the generated solution root:

```bash
dotnet new modulith-feature --appName MyApp -n Payments
```

Produces `src/Features/Payments/MyApp.Features.Payments.{Domain,Application,Infrastructure,Web}`
and registers all four in `MyApp.slnx` under a `/src/Features/Payments/` solution folder.

> The CLI option is **`--appName`** (short **`-ap`**), not `--app-name` — the template
> engine keeps the symbol name as-is (verified, see below).

## Verification (performed 2026-07-20, .NET SDK 10.0.300)

A throwaway copy of this exact template design was built and exercised end to end:

1. `dotnet new modulith -n MyApp` → clean, no `ModulithTemplate` leaks.
2. `dotnet new modulith-feature --appName MyApp -n Payments` from the solution root →
   four `MyApp.Features.Payments.*` projects created; no `ModulithApp`/`FeatureName` leaks.
3. **Post-action** added all four projects to `MyApp.slnx` and **auto-created the nested
   `/src/Features/Payments/` solution folder** from the project paths — no explicit
   `solutionFolder` arg needed; matches the existing Orders convention.
4. `dotnet build MyApp.slnx -warnaserror` → **0 warnings, 0 errors**.
5. `dotnet test MyApp.slnx` → **5/5 passed** (architecture tests discovered the new feature
   generically and its layering/isolation rules held).

### Confirmed facts (previously open risks)

- CLI option name is `--appName` / `-ap`, not `--app-name`.
- Post-action `D396686C…` works with `.slnx` on the net10 SDK and derives the correct
  nested solution folder from the project path.
- `preferNameDirectory: false` + baked `src/Features/FeatureName/` path places projects
  correctly when run from the solution root with no `-o`.

### Residual low-risk item to confirm during implementation

- The end-to-end **packed `.nupkg`** carrying *both* templates (verification above installed
  the two template roots separately from source). Microsoft's own tutorial packs multiple
  templates into one package, so this is expected to work; confirm by `dotnet pack` +
  `dotnet new install Modulith.*.nupkg` and checking both `modulith` and `modulith-feature`
  appear.

## Testing strategy for the implementation

Manual, via the commands in the repo's root `CLAUDE.md` (`dotnet new install` from source /
from the packed `.nupkg`, scaffold into a temp dir, build `-warnaserror`, test, grep for
stray tokens, uninstall). A future enhancement could add a CI job that scaffolds a solution,
adds a feature, and builds it, but that is out of scope for this change.
